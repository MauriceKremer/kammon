The Web Monitor

KAMmon

A calm console for one KAM node: what the radio hears, how the channel is used, and what the channels, rooms and scripts are doing.

Working monitorFor operators and beginners. Demo mode, login, and the Overview, Traffic, Channels, Rooms and Automations pages are built; the KISS modem and Accounts pages are placeholders for their slices.

What KAMmon Is

KAMmon is a website that shows one KAM node at work. It runs on the same computer as KAM and talks to it over KAM's local REST API: it asks KAM what the radio heard, how busy the channel is, who the rooms' clients are, and which scripts are installed. You look at the screens and, when you are an administrator, you change things from them.

KAM does the radio work. KAMmon provides the web interface. KAM starts, receives, stores messages and runs scripts without KAMmon. It does not register KAMmon as a client, check whether KAMmon is alive, or wait for it to read anything. A stopped or slow KAMmon changes nothing for KAM.

The screens are written for hobbyists. They explain themselves in plain words and repeat what the numbers actually mean: "Remembered clients" is not "online", and "Echo matches" is not "verified". When KAM has not answered for a while, the pages say so instead of pretending the numbers are current.

KAMmon is not a message archive, a chat application, or a second copy of KAM. It holds no database: its history lives in memory and starts again after a restart. Writing to kam.yml, the radio, the channels and the database stay KAM's job.

How It Behaves

Calm and dense

The interface is a quiet charcoal console. Small text, no cards and no decoration: one-pixel rules separate regions, and hierarchy comes from type size and spacing. The headings use a wide face and stay short. Dark is the default; a button switches to light, and the first visit follows the computer's own preference.

Honest labels

Every screen says what a number means. Remembered clients counts room clients KAM still knows about, including ones that have gone quiet — it is not "online". Last heard is the last request this node received from a client, not proof it is listening now. Estimated airtime comes from a formula, not from the radio. Echo matches means the modem returned the value it was sent; the radio chip may still have rejected it. A dot legend explains the activity states wherever they appear.

Read first, change second

Every page works as a read-only view for a signed-in viewer. Controls that change something appear only for administrators, and the server refuses those routes to other roles instead of merely hiding the buttons. Anything that touches the radio goes through a preview dialog that shows the exact commands before they are sent, with Cancel and Apply; the preview text comes from KAM, because KAM owns the protocol.

Simple on purpose

KAMmon is one Go program, one settings file and one stylesheet. Pages are rendered on the server; a small vendored script refreshes parts of a page every two seconds. Charts are drawn on the server as SVG. There is no database, no front-end build step and nothing loaded from a CDN.

What the Pages Show

Sign-in is separate from the radio. A web login is a KAMmon account. A room client login, a channel key and a script are all KAM things. A web role never changes a radio role.

The sidebar keeps a small node block: the node name, link state, radio summary and uptime. Administrators also see server statistics — the memory and runtime of the computer KAMmon itself runs on, not of KAM.

Try It in Demo Mode

Demo mode starts a fake KAM with generated traffic, so no radio is needed. You need Go 1.25 or newer:

go run ./cmd/kammon -demo

Open http://127.0.0.1:8080 in a browser. Two accounts exist for the demo: admin / admin is an administrator, and viewer / viewer can look only. Starting a server on a port your computer already uses fails with an address-in-use error; stop the other process first, or pass a different address. Demo mode answers every page from generated data, so no message you see came from a radio.

Stop the demo with Ctrl-C. If you lose track of a demo you started in the background, the repository's scripts/kill-kammon.sh stops it.

Viewers and Administrators

Users are written in the settings file, each with a role. Viewer means the pages answer as read-only views: counts, airtime, packet types, activity times, keys and radio state. Admin means every page plus everything a viewer sees — channel message text, room posts, client labels and every control.

  • A role belongs to the user, and admin power needs nothing more. KAMmon adds no transport rules of its own: an administrator signs in from any address and keeps that power.
  • Channel text reaches a viewer only for channels named in viewer_text_channels, an allow list in the settings file. Everyone else sees metadata — that a message happened — without its content.
  • The server decides. Every route knows its required role, and a viewer request to an administrator page is refused with an "administrator only" answer, not a hidden control.
  • Room protocol roles are read-only. Removing a room client deletes its session; that client is gone only after KAM confirms. A removed client can log in again under the room's own rules, because its credentials were never deleted.
  • Repeated failed logins from one address are slowed down; sessions expire after an idle time and live only in memory, so a restart signs everyone out.

Run Against a Real KAM

The commands below assume macOS or Linux and that the terminal is in the KAMmon project folder.

1. Make your own settings file

Copy the supplied configuration once, before editing it. If kammon.local.yml already exists, keep that file instead of overwriting your settings.

cp kammon.yml kammon.local.yml

Open kammon.local.yml in a text editor and review these values rather than accepting the example unchanged:

SettingMeaning and action
usersThe web accounts. Choose real passwords; the example's change-me is not a password anyone should keep. Passwords are plain text in the file, like KAM's channel keys in kam.yml.
listenThe address KAMmon serves, :8080 by default. A leading colon means every network interface — tighten it to 127.0.0.1:8080 if only this computer should reach the site.
kam_monitor_urlWhere KAM's API listens, http://127.0.0.1:8766 by default. KAM and KAMmon usually share one machine, so the loopback address is right.
viewer_text_channelsThe channels whose message text a web viewer may read; the default is #public.
pollHow often KAMmon asks KAM for each kind of data, each read's timeout, and how long to wait after a 404 answer before asking again. Leave a line out to keep its default.
freshnessWhen a reading stops counting as fresh: stale_after adds a "slow to answer" note, down_after marks KAM as down.
session_idle_hoursHow long a signed-in browser stays signed in without activity.

2. Start KAM first

KAMmon reads from KAM; it cannot receive alone. Start KAM as usual (its API listener is on by default on port 8766), and leave it running. KAMmon starting first only shows a down message until KAM answers.

3. Start KAMmon

go run ./cmd/kammon -config kammon.local.yml

Sign in with one of the users you wrote into the settings file. The site is a working monitor: nothing it shows comes from the demo generator, and a control appears only after the matching KAM feature has answered once. A page the running KAM does not serve shows a muted line, "Needs a newer KAM", instead of empty numbers.

Serving beyond your LAN is your choice to make safely. The site has login and session checks, but the operator owns the transport: put HTTPS in place first (KAMmon can serve tls_cert/tls_key itself, or run behind a reverse proxy) before exposing anything to the internet.

What KAMmon Remembers

KAMmon keeps no database. Charts, history and room tables are built in memory with hard limits: a bounded event ring and room-per-minute buckets, roughly a day at best. The history is labelled where it is shorter ("History starts at 14:03"), because a chart that begins mid-hour must not pretend otherwise.

A restart, or a period when KAM was down, leaves gaps. KAMmon backfills what it can from KAM's own event ring and draws marks where its history starts or where data is missing. The numbers on screen are a read of what this node observed: KAM hears only what reaches its antenna.

A snapshot can be slow or down. When KAM stops answering within the freshness limits, every page shows a ruled bar — "slow to answer", then "down" — and keeps the last numbers visible while marking the time they were taken.

KAMmon Is a Client

KAM serves one local REST API and does not know KAMmon exists. Nothing in KAM stores state for KAMmon, subscribes to it, or waits for it: the API keeps its event ring full whether or not anyone reads it, and the oldest events are replaced first. KAMmon is a reader with permission to send some changes, and KAMmon keeps every conclusion it draws in its own memory.

This separation goes both ways. You can stop KAMmon for hours and KAM keeps receiving, storing and running scripts. You can run a different client against the same API — the backend API manual describes what a client may ask for. And KAMmon holds none of KAM's data on disk: a restart costs the session logins and the in-memory history, then it rebuilds from KAM.

Privacy and Limits

  • Passwords are plain text. Web users, like channel keys and room passwords, live in readable settings files. Protect the machine and the files; the format does not hide anything.
  • An admin is an admin from anywhere. The web role travels with the user and adds no network conditions. Only sign in as an administrator from a computer and network you trust.
  • KAM's own API has no authentication. It listens on loopback, and any local program can read or change what it serves. KAMmon's login protects its own screens, not KAM.
  • Viewers are filtered at render, not at KAM. KAM returns full data to KAMmon; the allow list decides what each browser sees. The filtering is server-side, so a viewer cannot read restricted text by editing the page.
  • Radio text is unverified input. Message bodies and senders come from the air; the site escapes them when rendering and never trusts them as structure.
  • The console shows one hop. Signal strength is not displayed on traffic lists: it describes the hop the measurement was taken at, usually a nearby repeater, not the original sender's link.
  • History is short by design. In-memory history ends with the process. For a lasting record, use KAM's SQLite database; for a shareable board, KAM's room servers are the tool.

Troubleshooting

The pages say KAM is down or slow to answer

Check that the KAM process is running and that kam_monitor_url points at it. A fresh KAMmon may out-ask an older KAM: the address it polls then answers 404, the poller pauses that read for not_served, and the pages say "Needs a newer KAM". Update KAM to gain the missing surface.

Sign-in fails

Confirm the user and password against the settings file KAMmon was started with, and that the role line is intact. Repeated failures from one address are deliberately slowed; wait a moment and try again. A restart of KAMmon signs everyone out, because sessions live only in memory.

Channel text is missing on the Traffic page

Text is shown to viewers only for channels in viewer_text_channels, and to administrators everywhere. If the channel is absent from the list, check that the running KAM actually decrypts it — KAMmon cannot show text KAM could not decode.

A control does nothing

Controls that change something answer in place, and a failure keeps your input visible. A "Changed elsewhere" answer means another save happened first: reload the page to see the current version, then apply your change again. A control about modem radio first shows the exact commands in a preview; check that dialog before applying.

The demo will not start

An address-in-use error means the port is taken; stop the other process or choose another address. Demo mode needs no radio and no KAM, but it does need a Go toolchain to build. Stopping with Ctrl-C is enough; scripts/kill-kammon.sh stops a lost background process.

Glossary and Sources

TermPlain-language meaning
KAM APIThe local REST interface KAM serves on port 8766; the one address KAMmon reads.
PollerThe single part of KAMmon that asks KAM for data, on intervals set in kammon.yml.
StoreKAMmon's memory: the event ring, minute buckets and latest snapshots. Nothing here is on disk.
Fresh / stale / downThe three ages of a snapshot: answered recently; answered slowly, so pages say "slow to answer"; not answering, so pages say KAM appears down.
Viewer / AdminThe two web roles. A viewer reads metadata and allow-listed channel text; an admin sees everything and may change things.
Allow listviewer_text_channels in the settings file: the channels whose text a web viewer may read.
